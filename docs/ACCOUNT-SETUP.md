# Общий кабинет пары: настройка с iPhone

Код кабинета готов для Cloudflare Pages Functions и D1. Он **не подключён к реальным аккаунтам Яндекса и Mail.ru, пока не созданы приложения OAuth и не добавлены серверные настройки**. Без них кнопки входа отключены; планировщиком можно пользоваться без регистрации на текущем устройстве. Собственный домен и отправка писем для этого варианта входа не требуются.

Один вход создаёт один кабинет с двумя профилями предпочтений. Повторный вход через **тот же аккаунт того же провайдера** с другого устройства открывает те же маршруты. Вход через другой аккаунт или другой сервис создаёт отдельный кабинет; почтовые адреса автоматически не связываются. Пароли Яндекса и Mail.ru наш сайт не запрашивает и не получает.

## Сначала проверочная публикация

Рабочая публикация `https://bez-planov.pages.dev` остаётся на `main`. Новая версия подготовлена в ветке `feat/simple-couple-planner`. До переноса в main проверьте её на отдельном preview Cloudflare Pages.

1. Откройте в Safari [Cloudflare Dashboard](https://dash.cloudflare.com/), выберите **Workers & Pages → bez-planov**.
2. Убедитесь, что Production branch остаётся `main`. В настройках Branch deployments разрешите preview для `feat/simple-couple-planner`, если preview не создаётся автоматически.
3. После сборки откройте preview и скопируйте его **постоянный адрес ветки**, указанный Cloudflare. Используйте именно этот адрес, а не случайный адрес конкретной сборки. Название алиаса берите из панели Cloudflare.
4. Для preview заведите отдельную D1-базу и отдельные приложения OAuth либо отдельные разрешённые callback-адреса. Не используйте производственную базу для тестов.

## 1. База данных D1

1. В Cloudflare откройте **Storage & databases → D1 → Create database**. Создайте базу, например `bez-planov-preview`. Достаточно доступного бесплатного плана; платный тариф не нужен для подготовки. Если панель предлагает оплату или повышение тарифа, не подтверждайте его автоматически.
2. Откройте SQL Console новой базы. В GitHub откройте файл [`migrations/0001_accounts.sql`](../migrations/0001_accounts.sql), скопируйте его содержимое и выполните в консоли. При необходимости Safari → **аА → Запросить настольный веб-сайт**.
3. Вернитесь в Pages → bez-planov → Settings → Bindings. В окружении **Preview** добавьте D1 binding с именем **`DB`**, выбрав созданную базу.
4. Для production позже создайте отдельную базу `bez-planov`, примените ту же миграцию и добавьте binding `DB` в **Production**. Приложение использует только этот binding и не содержит идентификатора чужой базы.

Если используете терминал, альтернативный способ применения миграций — `wrangler d1 migrations apply <database-name> --remote`; сначала проверьте имя базы и окружение. На iPhone терминал не обязателен.

## 2. Яндекс ID

1. Откройте [кабинет Яндекс OAuth](https://oauth.yandex.ru/) под владельцем проекта и создайте приложение.
2. Укажите название «Без планов», платформу веб-сервиса и адрес сайта соответствующего окружения.
3. Разрешите только чтение базовых данных и адреса почты: **`login:info` и `login:email`**. Доступ к письмам, диску и контактам не нужен.
4. Укажите точный Redirect URI для production:

   `https://bez-planov.pages.dev/api/auth/callback/yandex`

   Для preview добавьте `<постоянный-preview-origin>/api/auth/callback/yandex` без лишнего завершающего `/`. Если кабинет допускает только один адрес, создайте отдельное приложение для preview.
5. Скопируйте Client ID и Client secret **только в серверные настройки Cloudflare**, описанные ниже. Не вставляйте секрет в GitHub, клиентский JavaScript, переписку или скриншот.
6. Если приложение требует активации или модерации, завершите её в кабинете провайдера. Пока провайдер не разрешил вход внешним пользователям, локальных тестов недостаточно для объявления регистрации рабочей.

Реализован authorization-code flow с PKCE S256 по [официальной документации Яндекса](https://yandex.ru/dev/id/doc/ru/codes/code-url); профиль запрашивается через [API Яндекс ID](https://yandex.ru/dev/id/doc/ru/user-information).

## 3. Mail.ru

1. Начните с [кабинета OAuth Mail](https://o2.mail.ru/app/) и [официальной справки Mail](https://help.mail.ru/developers/oauth/). Провайдер может перенаправить справку и регистрацию в кабинет VK ID. Используйте именно вариант **OAuth Mail**, а не произвольное приложение социальной сети.
2. Создайте веб-приложение «Без планов», запросив только право **`userinfo`**. Доступ к содержимому почты и IMAP не нужен.
3. Укажите точный callback production:

   `https://bez-planov.pages.dev/api/auth/callback/mailru`

   Для preview используйте `<постоянный-preview-origin>/api/auth/callback/mailru`. При необходимости заведите отдельное приложение.
4. Поместите Client ID и Client secret в Cloudflare. Пройдите требуемую провайдером активацию/модерацию.
5. Обязательно выполните настоящий пробный вход с разрешённым тестовым аккаунтом после настройки и затем с обычным аккаунтом, если приложение уже доступно всем.

Адаптер рассчитан на OAuth Mail с адресами `https://oauth.mail.ru/login`, `https://oauth.mail.ru/token` и `https://oauth.mail.ru/userinfo`. Их доступность и приём токена в POST-теле userinfo проверены без настоящих учётных данных; **полный вход с зарегистрированным приложением пока не проверен**. Текущая официальная справка Mail переводит на документацию VK ID. Если новый кабинет выдаёт иной тип приложения или иной протокол, этот адаптер нужно согласовать с выданными настройками до включения кнопки, а не подставлять случайные ключи.

Яндекс предоставляет стабильный ID пользователя. OAuth Mail может возвращать `sub`/`id`; если возвращается только `email`, адаптер использует подтверждённый прямым OAuth-запросом адрес как идентификатор **внутри Mail**, без связывания с Яндексом. При изменении такого адреса Mail-кабинет может определиться как новый — это ограничение email-only профиля провайдера.

## 4. Серверные переменные Cloudflare Pages

В Pages → bez-planov → Settings → Variables and Secrets добавьте значения **отдельно для Preview и Production**:

| Имя | Значение |
| --- | --- |
| `APP_ORIGIN` | Точный origin окружения без завершающего `/`. Для production: `https://bez-planov.pages.dev`. Для preview: постоянный адрес ветки из панели Cloudflare. |
| `YANDEX_CLIENT_ID` | Client ID приложения Яндекса для этого окружения. |
| `YANDEX_CLIENT_SECRET` | Client secret Яндекса, тип Secret/Encrypt. |
| `MAILRU_CLIENT_ID` | Client ID приложения OAuth Mail для этого окружения. |
| `MAILRU_CLIENT_SECRET` | Client secret Mail, тип Secret/Encrypt. |

Binding `DB` задаётся в разделе Bindings, а не строковой переменной. Значения client secret должны существовать только на сервере. Файл `.dev.vars.example` содержит только названия и пустые поля; `.dev.vars` исключён из Git.

Пересоберите соответствующий preview после изменения bindings и переменных. Без новой сборки серверные настройки могут не примениться. Сначала можно включить только одного провайдера: второй останется недоступным до настройки его пары ID/secret.

## 5. Проверка с двух устройств

1. Откройте preview в Safari, нажмите вход через настроенного провайдера, разрешите базовые данные и почту. После возврата должен открыться кабинет с адресом почты.
2. Создайте маршрут и сохраните его. Откройте тот же preview на другом устройстве/в другом браузере, войдите через **тот же аккаунт того же провайдера**. Проверьте, что маршрут доступен.
3. Измените данные в двух окнах, не обновляя одно из них. Сервер должен вернуть конфликт версии вместо молчаливого затирания изменений партнёра; интерфейс предлагает безопасно разрешить конфликт.
4. Войдите под другим аккаунтом: чужих маршрутов быть не должно.
5. Выйдите и перезагрузите страницу: доступ к данным общего кабинета должен исчезнуть. Вход гостем не должен показывать данные предыдущего аккаунта.
6. Проверьте оба OAuth-провайдера отдельно и отказ от разрешения на их экране. Только после этих проверок переносите изменения в main и повторяйте проверку production.

## Локальные тесты и ограничения

`npm run dev` поднимает локальный сервер на `127.0.0.1:8765`. По умолчанию вход отключён, как на ненастроенном production. Для тестов `NODE_ENV=test DEV_OAUTH=1 node scripts/dev-server.mjs` включает изолированный имитатор внешнего провайдера. Он существует только в локальном тестовом сервере: в Cloudflare Pages Functions нет тестового входа, кода-пароля или обхода OAuth. Тестовые сессии сохраняются в настоящем SQLite и проходят те же серверные проверки, что production.

Для ручных локальных тестов SQLite можно сохранить между запусками: `LOCAL_DB=.local/dev.sqlite npm run dev`. Этот файл исключён из Git. Без `LOCAL_DB` используется база в памяти.

Тесты кабинета: `node --test tests/account.test.mjs` (Node 24). Они проверяют session cookie, одноразовый OAuth state, PKCE, работу двух устройств, изоляцию аккаунтов, CSRF, конфликт версий, ограничение размера и выход. Эти тесты не доказывают готовность реального приложения провайдера или Cloudflare bindings.

Сервер хранит состояние пары в D1 и session-token hashes со сроком 30 дней. Cookies имеют HttpOnly, SameSite=Lax и Secure на HTTPS; OAuth-токены и коды не сохраняются в пользовательском состоянии и не выдаются в клиент. Протухшие session/state/rate-limit записи очищаются при начале входа. Автоматического объединения чужих кабинетов по совпавшей почте нет.
